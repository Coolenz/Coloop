# 本机交付约定

本文件约束在 `D:\Coloop` 工作的所有 agent。执行开发、测试、构建、部署或清理前，必须遵守下文“不保留 backup”及缓存存放规则：代码历史使用 Git；不长期保留任何构建或安装备份；可配置缓存统一放在 `D:\Coloop` 下，默认使用 `.cache`，不得沿用 C 盘默认缓存路径。无法安全重定向的例外必须按下文要求说明。

用户于 2026-11-06 明确要求：以后修改 Coloop 后，验证通过就直接替换本机安装版，不再只交付源码或独立 release 包，也不重复询问是否部署。

- 固定安装目录：`%LOCALAPPDATA%\Programs\Coloop`。桌面快捷方式与所有根目录 `start*.cmd` 统一启动这里的 `Coloop.exe`。
- 每次应用代码修改完成后，执行相应测试和 `npm run build`，将完整目录包构建到本轮专用的 release 暂存目录（默认 `release/current`，不得混入旧文件）。包含全部生产依赖和 `extraResources`，不可只覆盖 exe 或 out。暂存包只用于本轮验证和安装，不长期留存。
- 打包的 `afterPack` hook 必须补齐并校验生产依赖和必需 peerDependencies；不可仅在项目 release 子目录做启动验证，因为 Node 会向上借用开发目录依赖。
- 使用隔离的 `COLOOP_DATA_DIR` 验证目录包启动，并以 `COLOOP_EXECUTABLE` 指定实际安装路径运行 `tests/proactive-package-smoke.mjs`；相关改动涉及运行依赖时还需运行 `tests/runtime-package-smoke.mjs`。项目内包的验证不能代替实际安装路径验证，必须确认依赖均从包内加载。
- 使用 `scripts/install-local.ps1 -PackageDirectory <已验证的 win-unpacked 目录>` 替换安装版。不再创建或保留旧安装备份，也不在 C 盘创建安装暂存副本；完整同步后校验全部文件。失败必须报告，不能声称支持旧版回退。旧版 `app.asar` 不应混入新的非 asar 包。
- 安装前检查当前进程和任务；需要重启时先正常退出应用，不强杀正在执行的用户任务。然后验证实际安装路径并从统一入口启动。
- 完成时报告安装版验证结果、对应 Git 提交及构建副本清理结果；如果有实际阻塞，明确说明，不能把源码构建完成等同于部署完成。
- 仅文档修改不必重新打包。用户明确要求暂不部署时，以该次指示为准。

## 不保留 backup：适用边界与清单

用户于 2026-11-06 进一步明确：构建不需要备份，代码通过 Git 管理。本节覆盖此前“保留一个最新构建包”“保留最新 APK”“保留回退备份”等约定。

**长期只保留正在使用的安装版；源码历史交给 Git。** 本轮构建、验证、安装或交付所必需的临时产物可以短暂存在，但完成用途后必须删除，包括最新一份。不得将临时产物改名为 `backup`、`old`、`final`、日期目录或压缩包长期留存，也不得搬到 D 盘后继续充当备份。

本规则针对 Coloop 自动生成的安装副本、构建产物、验证副本与源码快照，不是删除用户文档、其他软件备份、系统还原文件或用户数据库的授权。

| 对象                                                                                       | 保留边界与处理方式                                                                                                    |
| ------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| 当前安装版 `%LOCALAPPDATA%\Programs\Coloop`                                                | 保留并使用；更新时完整替换、校验，不另外复制一份用于回退。                                                            |
| 旧安装副本，如 `Coloop-backup-*`、`Coloop.backup-*`、`Coloop-update-*`                     | 不创建、不保留，包括最近一份；发现历史残留时按安全清理流程删除。                                                      |
| 完整目录包，如 `release/current/win-unpacked`、`release/evolution-*`、`release/harness-*`  | 仅允许本轮待验证或待安装包临时存在；实际安装路径验证通过后删除全部暂存目录包，不能再保留“最新构建备份”。              |
| 安装或分发文件，如生成的 `.exe` 安装器、`.msi`、`.zip`、`.7z`、`.apk`                      | 只为当前明确的安装或交付需要临时生成；用途完成后删除。不能仅凭扩展名删除源码资源、用户文件或依赖中的同名格式文件。    |
| 完整验证副本，如 `Coloop-evolution-validation-*`、`Coloop-PackageValidation`               | 不另存长期副本；优先验证实际安装路径。确需临时副本时只放项目内，用完删除。                                            |
| 编译与测试中间产物，如 `out`、`dist`、Android `build`、临时测试 profile、解压/下载暂存文件 | 仅在当前开发或验收仍需要时保留；用途结束后清理，不按日期或版本累积。真实用户状态及费用账本不属于此类临时 profile。    |
| 源码、脚本、配置、锁文件、项目文档                                                         | 使用 Git commit/branch 记录变更与版本；不复制整个项目或打包源码 ZIP 当作备份，不丢弃用户未提交改动。                  |
| 当前所需依赖、模型及工具链，如 `node_modules`、Docling、Node、CUA、Android SDK             | 不是构建备份，保留必要的当前运行/开发依赖；仅清理确认无用的重复下载与历史副本，不能盲删整个 `.cache` 或全部依赖版本。 |
| 用户数据、密钥、记忆库、任务记录、恢复检查点、累计费用账本                                 | 不是可丢弃的构建缓存；不得因“不留 backup”而删除、重置或覆盖，也不得上传到 Git。数据迁移与数据保护须按具体任务处理。   |
| 小型验收报告、构建哈希、Git 提交号、必要日志与证据                                         | 可以保留用于追溯；不得把完整应用、依赖、模型或整份测试数据复制进去，伪装成验收证据长期存放。                          |

### Git 与恢复方式

- 可复现代码由 Git 提交、分支和锁文件保存；构建包、安装副本、模型、依赖缓存和含密钥的运行数据不提交 Git。
- 需要恢复旧代码时，从指定提交建立工作分支或采用明确的 Git 恢复操作，再重新构建、测试和安装；不依赖历史二进制包回退，不自动 `reset --hard`、`clean` 或覆盖用户未提交的修改。
- 安装或验证失败时如实报告当前状态，可以短暂保留正在排障的唯一候选包；明确用途和后续清理动作，不能自动恢复长期备份策略，也不能把失败的包记作已交付。

### 存放位置与清理顺序

- **缓存尽可能全部放在 D 盘，不放 C 盘。** 本项目任务产生的可配置缓存默认统一使用 `D:\Coloop\.cache`；范围包括包管理器、编译器、开发与验收工具、浏览器测试 profile、模型下载/解压缓存和临时文件。不能因为工具默认使用 C 盘，就直接沿用默认路径。
- 启动工具或子进程前优先设置其缓存路径及 `TEMP`、`TMP`、`TMPDIR` 等环境变量，并确认子进程继承；新增工具接入时也要检查实际落盘位置。需要缓存时直接在 D 盘创建，不先写到 C 盘再长期堆积或搬运。
- 对工具或系统固定管理、无法安全重定向的缓存，先查明可用配置；确实无法调整时记录位置、原因与清理方式，作为明确例外报告。不得为搬缓存破坏正在运行的工具、擅自迁移系统目录，或把用户数据、密钥与费用账本当缓存处理。
- C 盘的 Coloop 程序副本只允许当前安装目录；禁止在 Programs 或 Temp 创建第二份完整程序。`%APPDATA%\coloop` 的既有用户数据不作为缓存清理，也不因本规则擅自迁移。
- 本机所有 Coloop 开发、下载、测试、构建和验证缓存只能放在 `D:\Coloop` 下。使用项目 npm 脚本，或 `node scripts/with-workspace-cache.mjs <脚本> ...`；临时目录及 npm/pip/Electron 等下载缓存统一在 `.cache`。直接调用 PowerShell 工具前加载 `scripts/workspace-cache.ps1`。应用运行缓存的后续改动也必须遵守此位置约束。
- 禁止把完整验证包放到 `D:\Coloop-PackageValidation` 等项目外目录。开发目录外的独立验证使用实际安装路径；测试 profile、临时文件和证据仍放在项目内。
- 顺序为：记录源码版本 → 构建本轮包 → 验证 → 安装 → 实际安装路径验收 → 保存必要报告与哈希 → 清理本轮及历史构建副本。不得提前删除仍被当前任务使用的文件。
- `scripts/install-local.ps1` 不创建备份，完成同步校验后报告 `pending_installed_acceptance`；先完成实际安装路径验收，再执行 `scripts/prune-local-builds.ps1 -KeepPackageDirectory <本轮 win-unpacked> -IncludeCurrent`，清理本轮和历史桌面包。省略 `-IncludeCurrent` 只会清理旧包，不代表收尾完成。分发文件与未被脚本识别的历史残留也需核对并清理，脚本行为不能覆盖本约定。
- 删除前核对绝对路径、链接、活动进程、用途和保护清单；名称包含 `backup` 或文件时间较旧，不足以直接判定可删。清理必须限定在已确认的 Coloop 产物范围内。
- 系统拒绝的删除不得换工具绕过；报告未删除路径和具体阻塞原因，不把未执行的清理记作完成。完成报告应说明当前安装版保留情况及临时构建是否已清空。
