# Coloop Agent 工作约定

## 适用范围与执行优先级

本文件适用于在 `D:\Coloop` 工作的所有 agent，并持续适用于后续会话和任务，直至用户明确修改约定。

- 用户当次明确要求暂不测试、构建或部署时，按当次指示执行，并报告相应未验证范围。
- 默认交付流程为修改代码、测试、构建、验证、替换本机安装版、安装后验收及清理。验证通过后直接部署，无需重复询问。
- 仅文档修改不必重新打包。
- 开发、下载、测试、构建、部署及清理均须遵守下文的缓存位置、产物保留和数据保护要求。

部署、缓存及产物保留约定依据用户于 2026-11-06 的要求。DSH 接入及 CLI 约定依据用户于 2026-11-07 的要求。

## DSH 架构接入

- 新功能优先使用 DSH 原生能力和扩展点，包括会话、工具注册、执行循环及生命周期钩子。
- DSH 缺少合适的原生接入方式时，只增加必要的薄适配层，复用现有服务和业务实现。
- 接入以最小必要改动为原则，避免为适配 DSH 大规模重写现有模块或另建一套执行循环。

## CLI 与 AI 调用

全部功能应支持 CLI 或命令行操作，方便调试和 AI 调用。新增或修改功能时，同步提供可发现的命令入口、参数说明和结果反馈，使完整业务操作可以通过命令行完成。

### 操作入口与参数

- 操作 Coloop 前阅读 CLI 操作手册。[CLI 操作手册](docs/cli.md)
- 项目入口为 `D:\Coloop\coloop.cmd`，指向固定安装目录内的 CLI 和 Node。完整安装包也提供根目录 `coloop.cmd`。
- 常用操作顺序为 `coloop.cmd start` → `coloop.cmd status` → `coloop.cmd commands` → `coloop.cmd help <组> <操作>`。依据当前运行实例返回的 JSON Schema 构造参数。
- 开发源码入口为 `npm run --silent cli -- <命令>`，或 `node scripts/with-workspace-cache.mjs scripts/coloop-cli.mjs <命令>`。源码客户端需要连接包含相应接口的应用实例，安装版能力以实际返回的命令目录为准。
- 用 `--stdin` 或 `--file` 传入一个 JSON 值，字符串可用 `--string`。PowerShell 管道传递中文前设置 UTF-8 编码。密码、API Key 等敏感值通过标准输入或受保护的输入文件传入。
- `--data-dir` 与 `COLOOP_DATA_DIR` 选择应用数据目录。`--connection` 可选择已有实例的发现文件，启动新实例时须与所选数据目录一致。开发和验收 profile 放在 `D:\Coloop` 内。

### 结果与任务状态

- 普通命令读取 `ok`、`value`、`code`、`error` 和退出码。任务启动后保存任务 ID，通过 `task wait` 或 `auto-agent wait` 跟进，并按任务来源读取历史或后台任务状态。
- `watch` 和等待命令输出 JSON Lines。暂停、等待用户输入和输入结果待确认各有独立状态，按实际状态处理。退出 CLI 监听后，运行任务仍由应用管理。
- `OUTCOME_UNKNOWN` 表示调用结果待确认，先查询状态、历史和回执。
- `app quit` 返回 `requested: true` 表示退出请求已受理。安装前仍须确认应用进程退出。

### 实现与文档同步

- 常规业务入口通过 `src/main/index.ts` 的 `handle` 同时接入 IPC 和命令注册表，复用已有服务、授权检查、并发互斥与数据持久化逻辑。
- 每个命令在 `src/main/services/command-catalog.ts` 中维护说明和输入 Schema，优先复用共享 Zod Schema。注册表应拒绝缺少目录定义的命令，避免将有参数接口错误公布为无参数接口。
- 文件选择、目录选择和保存对话框对应的功能须接受显式路径，使 CLI 调用者能直接提供完整输入。
- 专用私密窗口的功能通过鉴权本地命令调用原服务，保留现有凭据保护和输入核验。敏感输入的错误反馈须避免包含原始值。
- 命令行 stdout 用于结构化结果。总体帮助使用文本，单命令帮助提供 JSON Schema，持续状态使用 JSON Lines。分别表达命令受理、任务完成和实际效果核验状态。
- 新增或改变功能时，同步更新 `docs/cli.md` 的命令表、参数格式、返回结构、状态说明和可复制示例。复核主进程注册、命令目录、手册三者是否对应。
- CLI 包装脚本、客户端和缓存环境脚本随完整安装包交付。同步维护 `package.json`、`scripts/after-pack.cjs` 与 `scripts/install-local.ps1` 的资源及完整性要求。

## 路径与缓存管理

### 固定位置

| 用途                             | 位置与要求                                                                  |
| -------------------------------- | --------------------------------------------------------------------------- |
| 当前安装版                       | `%LOCALAPPDATA%\Programs\Coloop`                                            |
| 应用启动入口                     | 桌面快捷方式与项目根目录所有 `start*.cmd` 统一启动安装目录内的 `Coloop.exe` |
| 开发、下载、测试、构建和验证缓存 | 统一位于 `D:\Coloop` 下，默认使用 `D:\Coloop\.cache`                        |
| 本轮完整目录包                   | 默认使用 `release/current/win-unpacked`，构建前确保暂存目录不混入旧文件     |
| 测试 profile、临时文件和验收证据 | 位于 `D:\Coloop` 内                                                         |
| 既有用户数据                     | `%APPDATA%\coloop`，按用户数据保护要求处理                                  |

### 缓存设置与例外

- 缓存要求覆盖包管理器、编译器、开发与验收工具、浏览器测试 profile、模型下载和解压缓存、临时文件，以及后续新增或修改的应用运行缓存。
- 优先使用项目 npm 脚本，或 `node scripts/with-workspace-cache.mjs <脚本> ...`。直接调用 PowerShell 工具前加载 `scripts/workspace-cache.ps1`。
- 启动工具或子进程前设置可配置缓存路径及 `TEMP`、`TMP`、`TMPDIR` 等环境变量，并确认子进程继承。新增工具接入时检查实际落盘位置。
- 缓存直接创建在项目内，避免沿用 C 盘默认路径或先写入 C 盘再搬运。
- 工具或系统固定管理的缓存须先检查配置能力。确实无法安全重定向时，记录位置、原因和清理方式，作为明确例外报告。
- 禁止为迁移缓存破坏正在运行的工具、擅自迁移系统目录，或将用户数据、密钥及费用账本当作缓存处理。
- C 盘的 Coloop 程序副本仅保留当前安装目录。禁止在 Programs 或 Temp 中创建第二份完整程序或安装暂存副本。
- 完整验证包须位于项目内，禁止使用 `D:\Coloop-PackageValidation` 等项目外目录。开发目录外的独立验证使用实际安装路径。

## 测试、构建与本机部署

按以下顺序执行，并依据当次用户指示调整测试、构建或部署范围。

1. **记录源码版本**。使用 Git 记录本轮变更，保留用户已有的未提交修改。
2. **测试与构建**。应用代码修改完成后运行相应测试和 `npm run build`，将完整目录包构建到本轮专用 release 暂存目录。
3. **校验包完整性**。包含全部生产依赖和 `extraResources`。`afterPack` hook 必须补齐并校验生产依赖及必需的 `peerDependencies`。禁止仅覆盖 exe 或 `out`。
4. **验证候选包**。使用隔离的 `COLOOP_DATA_DIR` 验证目录包启动。项目内启动可能借用上层开发依赖，验收须确认依赖均从包内加载。
5. **检查运行状态**。安装前检查当前进程和任务。需要重启时先正常退出应用，禁止强杀正在执行的用户任务。
6. **替换安装版**。运行 `scripts/install-local.ps1 -PackageDirectory <已验证的 win-unpacked 目录>`。完整同步后校验全部文件，禁止创建旧安装备份，确保旧版 `app.asar` 不混入新的非 asar 包。
7. **验收实际安装路径**。以 `COLOOP_EXECUTABLE` 指定实际安装路径，运行 `tests/proactive-package-smoke.mjs`。改动涉及运行依赖时，另运行 `tests/runtime-package-smoke.mjs`。项目内包验证须与安装路径验收分别完成，确认包内依赖加载后从统一入口启动应用。
8. **保存证据并清理**。保存必要的小型报告、构建哈希及 Git 提交号，再按下文清理本轮及历史构建副本。

安装脚本完成同步校验后报告 `pending_installed_acceptance`。完成实际安装路径验收后，才能将本轮交付记录为安装验收通过。

安装或验证失败时，如实报告当前状态和阻塞原因。排障期间允许短暂保留唯一候选包，须说明用途和后续清理动作。失败包不得记作已交付，也不得声称支持旧安装备份回退。

## 产物保留与安全清理

### 保留原则

长期仅保留正在使用的安装版，源码历史通过 Git 保存。本轮构建、验证、安装或明确交付所需的临时产物可短暂存在，用途完成后必须删除，包括最新一份。

本约定覆盖此前“保留一个最新构建包”“保留最新 APK”和“保留回退备份”等规则。禁止通过改名为 `backup`、`old`、`final`、日期目录、压缩包，或搬到 D 盘等方式长期保留构建备份。

清理范围仅限已确认的 Coloop 自动生成安装副本、构建产物、验证副本和源码快照。用户文档、其他软件备份、系统还原文件及用户数据库均受保护。

### 保留边界

| 对象                                                       | 保留与处理要求                                                                                                                             |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 当前安装版                                                 | 保留并使用，更新时完整替换和校验，不额外复制用于回退                                                                                       |
| 旧安装副本                                                 | `Coloop-backup-*`、`Coloop.backup-*`、`Coloop-update-*` 等经核实后清理，包括最近一份                                                       |
| 完整目录包                                                 | `release/current/win-unpacked`、`release/evolution-*`、`release/harness-*` 等仅供当前验证和安装，实际安装验收通过后删除全部暂存包          |
| 安装或分发文件                                             | 生成的 `.exe` 安装器、`.msi`、`.zip`、`.7z`、`.apk` 仅供当前明确的安装或交付需要，用完删除。禁止仅按扩展名删除源码资源、用户文件或依赖文件 |
| 完整验证副本                                               | 优先验证实际安装路径。确需 `Coloop-evolution-validation-*`、`Coloop-PackageValidation` 等临时副本时，仅放项目内并在用完后删除              |
| 编译与测试中间产物                                         | `out`、`dist`、Android `build`、临时测试 profile、下载和解压暂存文件，仅在当前开发或验收需要时保留，用途结束后清理                         |
| 源码、脚本、配置、锁文件和项目文档                         | 使用 Git 提交和分支保存历史，禁止复制整个项目或打包源码 ZIP 作为备份，保留用户未提交改动                                                   |
| 当前所需依赖、模型和工具链                                 | 保留必要的 `node_modules`、Docling、Node、CUA、Android SDK 等，仅清理已确认无用的重复下载与历史副本，禁止盲删整个 `.cache` 或全部依赖版本  |
| 用户数据、密钥、记忆库、任务记录、恢复检查点和累计费用账本 | 禁止因清理构建产物而删除、重置、覆盖或上传 Git。真实用户状态按具体任务的数据迁移和保护要求处理                                             |
| 小型验收报告、构建哈希、Git 提交号和必要日志               | 可以保留用于追溯。禁止将完整应用、依赖、模型或整份测试数据复制为长期验收证据                                                               |

### 清理流程

1. 删除前核对绝对路径、链接、活动进程、实际用途及上表中的保护对象。文件名包含 `backup` 或时间较旧，均不足以作为删除依据。
2. 安装候选包须先完成实际安装路径验收。其他临时产物在当前用途结束后清理，保留仍在使用的文件。失败候选包按排障期间的保留要求处理。
3. 运行 `scripts/prune-local-builds.ps1 -KeepPackageDirectory <本轮 win-unpacked> -IncludeCurrent`，清理本轮和历史桌面包。省略 `-IncludeCurrent` 仅清理旧包，收尾仍须包含本轮暂存包。
4. 另行核对分发文件和脚本未识别的历史残留。脚本结果须与本文件规定的清理范围一致。
5. 系统拒绝删除时，报告未删除路径和具体原因，禁止换工具绕过。仅将实际完成的删除记录为已清理。

## Git 与恢复

- 每次完成代码或文档修改后，将本轮变更提交并同步推送到 GitHub，无需再次询问。推送后核对远端提交，完成报告包含提交号与同步结果。推送失败时保留本地提交并说明原因。
- 同步最新已完成源码、必要脚本、配置、锁文件及配套文档。保留用户已有未提交改动，提交前核对差异与敏感数据。
- 当前 GitHub 仓库为 `Coolenz/Coloop`，主分支使用 `Coloop/` 与 `RK/` 的合集结构。本地 `D:\Coloop` 应用源码对应远端 `Coloop/`，同步时保留仓库根目录展示页、配套 RK 源码及远端独有文档。
- 可复现代码通过 Git 提交、分支和锁文件保存。构建包、安装副本、模型、依赖缓存及含密钥的运行数据不得提交 Git。
- 恢复旧代码时，从指定提交建立工作分支或采用明确的 Git 恢复操作，再重新测试、构建和安装。
- 禁止自动执行 `reset --hard`、`clean` 或覆盖用户未提交修改。代码恢复通过 Git 和重新构建完成。

## 完成报告

完成时按本轮实际范围简要报告以下内容，并明确标注未执行、失败或受阻的步骤。

- 本轮修改范围与对应 Git 提交。
- 测试、源码构建、目录包验证及实际安装路径验收结果。
- 当前安装版的保留和使用情况。
- 本轮及历史临时产物的清理结果，包含保留项的用途、未删除路径和阻塞原因。

源码复核、源码构建、目录包验证和安装验收分别记录。用户要求暂不部署时，按实际完成范围报告。
