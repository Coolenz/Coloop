## 一次指令持续执行到完成

1. 每个用例创建 `.qa/violoop-functional/<run_id>/<case_id>/<attempt_id>/`，准备专用数据，保存初始文件摘要、页面和账号映射。`run_id` 与 `attempt_id` 必须唯一。
2. 将提示词中的任务目录、实际URL、T时刻、邮箱和用户ID等变量替换为本轮确定值，保存最终原文。禁止把尚未绑定的变量交给模型猜测。
3. 通过 Coloop 工作台输入框或手机输入框发送一次完整任务。保存消息ID、task_id、发送时间及账号。F01、F12、A03、A11与A12必须覆盖手机入口，其余用例覆盖桌面输入入口。A01按无提示主动建议入口执行。
4. 任务由模型自主规划并实际执行。按产品授权策略接纳任务或建议后，在授权范围内持续观察、操作、回读和修正。脚本、浏览器、软件API及键鼠路线均可，但每轮记录实际路线。
5. 普通网络、定位、导出、窗口切换和格式错误由系统自行恢复。用户仅补充真正缺失的业务信息、接入条件或既定确认，不逐步指挥点击。所有人工协助记录内容、时间及是否影响自主完成判定。
6. 超过预计总时长仍有真实进展则继续运行。等待用户回复保持任务，不设置7分钟或10分钟整任务终止阈值。单步超时用于诊断和恢复。
7. 连续15分钟没有有效新证据记为停滞诊断，保留任务。重复读取相同内容、重复报错和更新执行时间戳均不算业务进展。观察者核查目标、网络、页面与待回答问题，故障解除后继续。
8. 输入结果未知先检查真实业务状态，再决定是否补做。发送、创建、加购、邀请等操作都要核对已有记录，防止重放。服务或设备重启后的恢复遵循现有产品授权策略。
9. 产品自行检查全部交付条件后声明完成。独立验收方只读检查文件、刷新后的记录、接收端及最终回执，存在差异则将差异反馈到同一任务继续纠正并保留记录。
10. 产品任务终态、业务判据、独立证据和用户可见回执均满足，才记 `PASS`。主动停止请求始终有效。

连续性遵循仓库既有[任务连续性与交付判定](task-continuity-policy.md)。现有 [daily-life-round.mjs](../tests/daily-life-round.mjs) 可作为派发和观察实现参考，本套的真实账号准备、故障注入及业务核验仍须逐项接入。

## 执行路线与判定

- 每项至少运行一次正常主流程，并将每个恢复项作为独立尝试运行。A03、A08、A09、A10的各分支分别计分，不合并掩盖未通过项。
- 通用功能验收允许产品自行选择执行工具。若要验收硬件观察与HID能力，另开 `hid_only` 尝试，保留实际输入报告与观察记录，以该路线自己的结果计分。两条路线都使用产品正常发起入口。
- 验收方可准备数据、制造声明过的故障及只读取证。验收方直接填写业务数据的尝试记为有人工协助，保留原结果，并另开自主执行尝试。
- 公开网站动态数据以本轮同批快照为基线。无法登录或需验证时转 `WAITING_INPUT` 或 `BLOCKED` 并写明必要条件。使用本地副本时另记 `fixture`，真实站点覆盖仍待实测。
- Kickstarter FAQ将自动解锁描述为可选授权能力，A03分开验证未启用、启用授权及睡眠唤醒，逐步记录实际能力状态。[Kickstarter FAQ](https://www.kickstarter.com/projects/bvio/violoop-plug-in-ai-for-your-computer/faqs?category_id=52)
- 本轮将官网锁屏、物理按键、语音及Windows输入兼容目标作为独立能力验收。当前 Coloop 是否具备相应能力须实测确认，缺少硬件或环境的分支记录 `BLOCKED` 并保留在总体分母中。
- 每次尝试保留首次结果和后续修正。汇总同时给出首轮通过率与恢复后通过率，写明所有缺失能力、人工步骤及仍在运行的任务。

## 状态和结果记录

分别记录任务运行连续性与业务交付，避免将“仍在运行”当成交付通过。`STALLED`只作诊断，只有确实发生不可恢复终态错误时才记失败。外部条件阻塞与用户等待可恢复后继续。

| 维度     | 状态                                                         | 记录要求                               |
| -------- | ------------------------------------------------------------ | -------------------------------------- |
| 连续性   | RUNNING / WAITING_INPUT / STALLED / STOPPED / TERMINAL_ERROR | 业务进展时间、当前阶段、原因和恢复事件 |
| 交付     | NOT_RUN / PENDING / PASS / FAIL / BLOCKED                    | 每条判据、证据位置、独立核验结论       |
| 执行分支 | general / hid_only / fixture                                 | 路线、硬件、真实平台与人工参与         |

每次尝试保存 `prompt.txt`、`environment.json`、`timeline.jsonl`、业务产物和 `result.json`。环境至少包含系统与软件版本、桌面和手机构建摘要、RK固件及模型、实际云端模型标识、屏幕缩放、时区和执行路线。证据使用测试账户数据，报告中的账号使用别名。

`result.json`采用以下记录结构，字段中的空值在实际执行时补齐。

## 优先执行顺序

先执行A12接入首任务，再执行F01订单到台账及回复，随后执行F14文件整理与F16邮件附件归档。主线连通后运行F02至F12的中文业务覆盖及A01至A11能力恢复测试。每个任务从发令开始自行推进，普通恢复由系统处理，真正缺失的信息和既定业务确认在同一任务中补充。

F01核验台账和接收端，A08覆盖授权与停止，A06覆盖发送回执未知时的去重恢复。完整发送业务以接收端独立记录为准。
