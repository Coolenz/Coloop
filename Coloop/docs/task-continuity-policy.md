# 任务连续性与交付判定

用户于2026-11-04明确：任务超过预计时间，只要仍在实际推进，就不应被打断或判为失败。

- 总耗时只作记录，不设7/10分钟任务终止上限。旧验收清单的 `max_ms` 不再触发取消。
- 等待用户回答属于正常暂停，不再因等待45秒取消任务。回答后继续。
- 单次截图、OCR、网络请求或脚本超时仍可触发该步骤的检查和恢复，不代表整个任务失败；输入效果不明时先读回，避免重复操作。
- 连续性与交付分开：任务可处于“运行正常、结果待交付”；只有实际结果经核对才算交付完成。错误日期、错误地点或错误算式仍是结果质量问题。
- 验收驱动默认连续15分钟没有新证据时记为 `stalled` 诊断，任务保持运行；通过 `stall_timeout_ms` 可以调整观察窗口。有新进展后回到运行状态。

进展信号采用新的已核验读回或流式回答内容。相同事实的重复读取、执行ID/时间戳变化、报错重试和阶段反复切换都不单独刷新进度。证据暂时读不到就继续观察。计时不代替业务语义判断：新增内容不一定有用，需要结合目标复核。

当前驱动的证据观察主要覆盖本地脚本回执和回答。未接入回执的原生操作可能无法完整体现进展，因此停滞只是提示，不自动取消或报任务失败。主动停止继续有效。

实现：[验收驱动](../tests/daily-life-round.mjs)、[进展观察](../tests/daily-life-progress.mjs)。CPU和本地文件回归运行 `node --test tests/daily-life-progress.test.mjs`，覆盖长任务、新证据、重复事实、元数据变化、等待用户及证据文件暂不可读；不将这些回归称作整轮实机重测。
