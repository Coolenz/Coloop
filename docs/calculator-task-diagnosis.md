# 计算器分摊餐费原因分析

任务：286元餐费加24元停车费，5人平摊；正确目标为 `(286+24)/5=62`。分析来自任务 `c2e6ed3a-1aaa-4ee6-a731-20ba77a062e0` 的43个脚本步骤回执。

结论：**主要是模型编排的操作序列错误，伴随控件定位、清空和恢复适配问题。任务当时在持续执行，不是运行断开，也没有证据表明计算器自身算错。** 本项操作由PowerShell UI Automation直接调用Windows计算器控件，不是RK鼠标键盘发送链路。

## 可直接确认的原因

| 证据步骤 | 实际记录 | 含义 |
|---|---|---|
| `d6824af7-a490-4b6e-8555-8f89b2d6f883` | 每个数字/运算控件调用均返回True，但发送的是 `286 + 24 + 5 ÷ 5 =`，实际显示311 | 控件执行成功，操作计划本身多了“+5”，并没有实现均摊目标。 |
| `7482db3a-8e7a-41f5-b1cf-84844c04a9ba` | 脚本直接列出两遍286和24，实际表达式为 `286 + 24 + 286 + 24 ÷ 5 =`，显示600.8 | 600.8可由新发送的错误算式完整解释，不能仅归因于旧输入残留或焦点变化。 |
| `4a8e9db8-3164-4066-b148-f4554013eac0` | 找不到 `openParenButton` / `closeParenButton` 后仅打印MISS继续，后面又输入一遍286和24，出现24576.8 | 必需控件缺失后仍执行后续动作，造成漏括号、数字拼接和重复输入。 |
| `695cc349-3c76-4d17-a38d-7db93f16caa8` | 已枚举真实ID：`num2Button`、`num8Button`、`equalButton` | 控件信息可以实际读取。 |
| `f46f4cd8-fae2-454b-ae74-a4f421cdf8fb` 等后续步骤 | 再次使用不存在的 `twoButton`，报按钮缺失 | 恢复过程未稳定复用之前确认的信息，而不是单纯多等待即可解决。 |

当时窗口处于Scientific模式。[微软官方说明](https://github.com/microsoft/calculator)该模式按运算优先级计算。两次结果分别满足 `286+24+5/5=311` 和 `286+24+286+24/5=600.8`，与实际显示相符。

## 附带问题与判断边界

- 早期按CalculatorApp的主窗口句柄查找得到0，实际可见窗口由ApplicationFrameHost承载；一些后续尝试又回到错误进程/窗口定位方式。
- 日志确有SetFocus失败、UIA类型未加载、不支持的控件模式等错误。这些影响部分尝试，但解释不了控件已成功调用、算式也准确显示出来的两次错算。
- 清空函数有找到CE便停止或找不到Clear便继续的情况，缺少“显示0且整个表达式为空”的统一前置核对。CE是清除当前输入，不能无条件替代整体重置。不过600.8那次的主因仍是明确写错的新输入序列。
- 多数目标结果核验返回False，没有将错误数值认定为62；少数探测步骤的verified=True只证明取到窗口或控件信息，不证明餐费计算已完成。
- 此前“最终显示600.8”的表述应修正：600.8是结果文件中保留的一次错误值；最后一份实时探测 `e6646218-c300-4705-80d4-bf26be0514d2` 已读到显示0。没有取得62的证据。

## 应修复的方向

将目标先编排为两个可核对阶段：算出总额310，再除以5得到62。执行前读取真实控件映射并确认所有必需控件存在；重置后核对显示值及表达式；每阶段按实际读回决定下一步。控件缺失时放弃未执行部分并重新观察，不跳过后继续拼接输入。恢复时保留已经确认的控件信息，并在窗口身份改变后重新验证。

本次已经调整的是[连续性判定](task-continuity-policy.md)。计算器操作规划和控件适配的问题在此报告中定位，尚未宣称修复或实机复测成功。
